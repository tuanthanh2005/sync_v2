# SyncViet Financial Security Controls

## 1. Threat Model & Mitigations

| Attack Vector                               | Defense Implemented                                                                                                                                                                                                                                          |
| :------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Client Price / Amount Tampering**         | Server always resolves authoritative integer pricing from `premium_plans`, `banner_placements`, and `boost_packages`. Client `amount` fields are ignored on catalog checkouts.                                                                               |
| **Order Spam / Unpaid Pending Exhaustion**  | `MonetizationPaymentService` & `WalletService` lock `User::lockForUpdate()` inside `DB::transaction`, auto-expire stale 24h pending orders, and strictly cap open (`pending`/`processing`) orders at 5 per user.                                             |
| **Automatic / Accidental Order Creation**   | Frontend requires explicit Yes/No `PaymentConfirmModal` and backend validates `confirmed: accepted`.                                                                                                                                                         |
| **Fake Webhook / Replay Attack**            | `HmacPaymentWebhookService` verifies HMAC-SHA256 (`X-SyncViet-Timestamp`, `X-SyncViet-Signature`) with ±300s timestamp window, validates `amount === payment.amount`, enforces unique `provider_reference`, and logs all attempts to `payment_webhook_logs`. |
| **Double Activation / Double Credit**       | Unique `subscription_events(payment_id, event_type)` and `ad_credit_entries(idempotency_key)` + `Payment::lockForUpdate()` guarantee strictly-once fulfillment.                                                                                              |
| **Exclusive Banner Double Booking**         | `BannerPlacement::lockForUpdate()` inside `DB::transaction` validates zero overlapping schedules before saving or approving.                                                                                                                                 |
| **SSRF via Banner Creative / Target URL**   | `SafeLinkPreviewService::isSafePublicUrl()` blocks loopback, private RFC1918, CGNAT, and cloud metadata IPs; `SafeImageUploadService` strips EXIF and re-encodes via GD.                                                                                     |
| **IDOR on Payment Receipts / Cancellation** | `PaymentHistoryController` verifies `$payment->user_id === $user->id` (or authorized finance staff) returning `403` otherwise.                                                                                                                               |
| **Unauthorized Admin / Missing 2FA**        | All `/admin/monetization/*` routes require `admin.2fa`, `can:access-admin`, and granular `permission:*` middleware. Manual payment reconciliation and refunds additionally require Admin password confirmation and write immutable `audit_logs`.             |
| **CSV Formula Injection**                   | `RevenueAnalyticsService::exportMonetizationCsv()` neutralizes cells starting with `=`, `+`, `-`, `@`, `\t`, `\r`.                                                                                                                                           |
